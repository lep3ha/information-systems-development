# Супермаркет — лабораторная работа № 1

Flask-приложение с главным меню и тремя параметризованными запросами к PostgreSQL:

1. Товары выбранной категории.
2. Поставщики из выбранного города.
3. Поставки выбранного поставщика за период с суммой каждой поставки.

## Запуск одной командой через Docker

Установите Docker с Docker Compose. Из корня проекта выполните:

```bash
docker compose up --build
```

Откройте `http://127.0.0.1:5000/` на компьютере, где запущен Docker.
Если Docker работает на VPS, а браузер — на вашем компьютере, сначала
пробросьте порт через Remote SSH, как описано ниже.

Compose запускает Flask и PostgreSQL 17. При первом запуске автоматически создаются
таблицы и загружаются контрольные данные. Настройки подключения уже подготовлены
в `docker/db_config.json`; вручную создавать конфигурацию или БД не требуется.
Приложение запускается после готовности PostgreSQL. Используется обычный сервер
разработки Flask.

Данные БД сохраняются в volume `postgres_data` между запусками. SQL-скрипты
инициализации выполняются только при создании новой БД.

Для остановки нажмите Ctrl+C, затем удалите остановленные контейнеры:

```bash
docker compose down
```

Для полного сброса **с удалением данных БД**:

```bash
docker compose down -v
```

Проверки приложения и реального PostgreSQL в работающих контейнерах:

```bash
docker compose exec -e LAB1_TEST_DB_CONFIG=app/data/db_config.json web python -m unittest discover -v
```

### Работа через VS Code Remote SSH

В `compose.yaml` порт приложения опубликован на `127.0.0.1:5000` VPS.
Чтобы открыть его в браузере своего компьютера:

1. Подключитесь к VPS через VS Code Remote SSH и запустите `docker compose up --build`.
   Оставьте команду работающей.
2. Нажмите F1 и выполните команду `Ports: Focus on Ports View`.
3. Во вкладке **Ports / Порты** нажмите **Forward a Port / Пробросить порт**
   и введите `5000`.
4. Откройте локальный адрес, который покажет VS Code, обычно `http://localhost:5000/`.
   Если этот порт на вашем компьютере занят, VS Code может назначить другой —
   используйте адрес из вкладки **Ports**.

Чтобы VS Code восстанавливал проброс при подключении, включите настройку
**Remote: Restore Forwarded Ports**.
Подробнее: [проброс портов через Remote SSH](https://code.visualstudio.com/docs/remote/ssh#forwarding-a-port--creating-ssh-tunnel).

## Подготовка без Docker

Нужны Python 3.12, PostgreSQL с поддержкой часового пояса `Europe/Moscow` и клиент `psql`.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Создайте пустую БД `supermarket` и пользователя с правами создания таблиц в ней.
Скопируйте `app/data/db_config.example.json` в `app/data/db_config.json` и задайте
свои параметры подключения. Рабочий файл конфигурации исключён из Git.

Через `psql` подключитесь к этой БД. Для свежей пустой схемы выполните из корня проекта:

```sql
\set ON_ERROR_STOP on
\i app/db/db_data/tables.sql
\i app/db/db_data/input_data.sql
```

Скрипты запускаются по одному разу в указанном порядке. Каждый выполняется в транзакции.
Данные рассчитаны на новую схему с автоматически назначенными идентификаторами от 1.

## Запуск

Из корня проекта:

```bash
.venv/bin/python -m app.main_menu
```

Откройте `http://127.0.0.1:5000/`. Главное меню ведёт к запросам или к сообщению
«До свидания». Формы открываются через GET, запросы выполняются через POST.
SQL хранится отдельно; значения передаются драйверу параметрами.

Для дат поставок используется московское время; обе граничные даты включаются целиком.
Неверные параметры возвращают форму с сообщением и кодом HTTP 400. Пустая выборка
показывает «Ничего не найдено» с HTTP 200. При ошибке БД форма сохраняет введённые
значения и возвращает общее сообщение с HTTP 503; подробности пишутся в журнал сервера.
Без рабочего файла конфигурации меню и формы доступны, выполнение запроса возвращает HTTP 503.

## Как связаны HTML-файлы

Шаблоны обрабатывает Jinja2 на сервере. `render_template(...)` собирает готовую
HTML-страницу и Flask отправляет её браузеру. Выражения `{{ ... }}` подставляют
значения, а конструкции `{% ... %}` управляют сборкой страницы. Браузер получает
результат этой обработки.

| Файл | Назначение |
|---|---|
| `app/templates/base.html` | Общий каркас: `html`, `head`, кодировка, заголовок вкладки, `body` и место для содержимого |
| `app/templates/main_menu.html` | Главное меню: ссылки на запросы и завершение работы |
| `app/templates/exit.html` | Страница «До свидания» |
| `app/query_bp/templates/query_menu.html` | Список трёх запросов со ссылками на их формы |
| `app/query_bp/templates/query_form.html` | Общая форма: название запроса, место для полей, кнопка отправки, ошибки и ссылки возврата |
| `app/query_bp/templates/products.html` | Поле «Код категории» для запроса товаров |
| `app/query_bp/templates/suppliers.html` | Поле «Город» для запроса поставщиков |
| `app/query_bp/templates/deliveries.html` | Поля кода поставщика и начальной/конечной дат |
| `app/query_bp/templates/query_result.html` | Таблица результата или «Ничего не найдено», ссылки повтора и возврата |

`products.html`, `suppliers.html` и `deliveries.html` наследуют `query_form.html`,
а он наследует `base.html`. Остальные страницы наследуют `base.html` напрямую.
`{% extends ... %}` выбирает родительский шаблон; `{% block fields %}` в конкретной
форме заполняет место для полей, объявленное в `query_form.html`.

Пример работы запроса товаров:

1. Ссылка в меню отправляет `GET /query/products`.
2. `query_handler` выбирает `products.html` и вызывает `render_template`.
   Jinja2 объединяет его с `query_form.html` и `base.html`. Ответ — HTML-форма,
   HTTP 200. Запрос к БД на этом шаге не выполняется.
3. Пользователь вводит код категории и нажимает кнопку. Атрибуты `method="post"`
   и `action` у тега `form` направляют `POST /query/products` с полем `category_id`.
4. `query_handler` читает `request.form` и передаёт параметры в `model_route`.
   Модель проверяет их, получает SQL у `SQLProvider` и вызывает `select_list`.
   Эта функция выполняет SQL и возвращает список словарей с именами столбцов.
5. При успехе контроллер передаёт строки в `query_result.html`, и браузер получает
   таблицу либо «Ничего не найдено», HTTP 200.
6. При неверных параметрах контроллер снова отображает `products.html`, передавая
   `values` и `error`, HTTP 400. При ошибке БД возвращается такая же форма
   с общим сообщением и HTTP 503. Неизвестное имя запроса даёт HTTP 404.

`{{ url_for(...) }}` строит адрес ссылки или формы по имени обработчика.
`{% for ... %}` в шаблоне результата создаёт строки таблицы, а `{% if ... %}`
выбирает между таблицей, пустым результатом и показом сообщения об ошибке в форме.

## Контрольные примеры

| Запрос | Параметры | Ожидаемый результат |
|---|---|---|
| Товары категории | Код `1` | Молоко 1 л, Сыр 200 г |
| Товары категории | Код `4` | Ничего не найдено |
| Поставщики города | `Москва` | Молочный двор, Фруктовый сад |
| Поставки за период | Поставщик `1`, даты `2026-10-01` — `2026-10-31` | Поставки `1`, `2`, `3`; суммы `1700.00`, `1810.00`, `600.00` |
| Поставки за один день | Поставщик `1`, обе даты `2026-10-31` | Поставка `3`, сумма `600.00` |

Порядок строк не фиксируется. Поставка в полночь 1 ноября не входит в октябрь;
поставка в последнюю микросекунду 31 октября входит.

## Проверки

Проверки HTTP-сценариев с подменой доступа к БД и ошибок жизненного цикла транзакции:

```bash
.venv/bin/python -m unittest tests.test_lab1 -v
```

Для проверки реального PostgreSQL укажите путь к JSON-конфигурации **тестовой** БД.
Тесты создают временную схему `lab1_test_<uuid>`, загружают в неё SQL и данные,
проверяют запросы, ограничения и транзакции, затем удаляют эту схему.
Пользователю нужны права создания и удаления собственных схем.

```bash
LAB1_TEST_DB_CONFIG=app/data/db_config.json .venv/bin/python -m unittest discover -v
```

Без `LAB1_TEST_DB_CONFIG` проверки реального PostgreSQL явно пропускаются.
